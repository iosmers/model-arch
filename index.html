2 单层解剖 以 L3–L90 的 MoE 层为例

3 注意力：一套 GQA 底座，两条路径

92 层都是 GQA（64 Q / 4 KV，head_dim 192，Q/K 各自 Norm，输出逐 head 门控）。差别只在“能看到多少历史”。

Gated Sliding Window · 69 层

窗口512 token
RoPE全维 192，θ = 1e4
每 token 可见 keymin(T, 512)
代价O(T × 512)

门控是 attn_out * sigmoid(W_g x)，每个 head 一个标量。

示意：每行一个 query，高亮为可见 key；真实窗口 512

Sparse GQA（DSA 式）· 23 层

块大小 B8 token / 块
预算 k4096 token = 512 块
选择粒度4 个 KV 组各自独立选
indexer16 head · 256 维 · RoPE 32
本层 RoPE局部 64/192，θ = 1e7

主路径读的是原始 K/V（不是压缩块），只是读的范围被 indexer 裁到 512 个块 + 当前块内因果可见的位置。

示意：16 × 16 个块，每行选当前块 + 近块 + 若干远块；真实每行选 512 块

一个 token 在稀疏全文层里走过的 5 步

1
块内压缩

每 8 个连续 token 的 index key 压成 1 个块表示，indexer 的算力和 top-k 选择量直接降 8×。

2
indexer 打分

q 投影到 16 × 256，和块表示做点积；经 ssmax（每 Q head 一个可学习尺度）得到每头分数。

3
top-512 块

k = 4096 token ⇒ 选 512 个块；4 个 KV 组各自选自己的，互不共享。

4
相邻 token 取并集

相邻 token 选中的块高度重叠，kernel 把它们合成一次计算，避免碎片化导致 GPU 空转。

5
主注意力

对选中块读原始 K/V，再加上当前块里因果可见的位置，正常 GQA 计算。

所以「1M 要 276 GiB」只在「92 层都按全长存」时成立。按架构允许的最小值算，同一条 1M 序列是 69.1 GiB（BF16）——因为 69/92 层是 512 滑窗，只需要最近 512 个位置；滑窗部分整条序列加起来才 108.5 MB，可以忽略。能不能吃到这 4 倍，取决于推理引擎的 KV 管理：按层类型做环形缓冲/分类型分配就能吃到，统一按 max_model_len 预留就吃不到。
两个容易踩的点：
① Sparse GQA 省的是计算，不是存储——选块是从全部历史块里挑，所以 23 个全文层的 K/V 必须全量保留；真正省存储的是那 69 个滑窗层。
② TP 只能切到 4 路：KV 只有 4 个 head，TP ≥ 4 时每卡不再线性下降（每卡仍约 1/4，多出来的 rank 是复制）。1M 全量在 8 卡上是 ~69 GiB/卡，不是 34.5。
另外还有一项小开销：indexer 的 256 维 index key 若也缓存，23 层 × 256 × 2 B × T ≈ 12.3 GB（@1M，约占 4.5%）；只缓存每 8 token 压出来的块摘要则只有 ~1.5 GB。

4 MoE：88 层，每层 353 个专家

路由专家 352 个、每 token 命中 8 个；另有 1 个常开的共享专家。专家都是 SwiGLU，intermediate = 1536。

44 × 8 = 352 个路由专家，亮起的是某 token 命中的 8 个
router4096 → 352，FP32，带 bias
缩放moe_router_scaling_factor = 3.0
路由专家SwiGLU，d = 1536，clamp ±7
共享专家1 个，SwiGLU，d = 1536，常开
合并路由 + 共享 在 FP32 中相加
每 token 每层激活：8 × 18.87 M（路由）＋ 18.87 M（共享）≈ 170 M；乘 88 层 ≈ 14.9 B，是 27 B 激活参数里最大的一块。

视觉 token 数怎么来的

728 ÷ 14 = 5252² = 2704 patch→ 13² = 169
504 ÷ 14 = 3636² = 1296 patch→ 9² = 81

728×728 是一张「概览图」，出 169 个视觉 token；504×504 是若干个「切片」，每片出 81 个。它们和文本 token 一样走同一条 92 层主干。

视觉塔参数只占全模型 0.33%，但它的 47 层是纯 dense 结构，没有 MoE 也没有滑窗/稀疏的区分。

6 MTP：3 层，每层自带一份 LM Head 2.52 B · 只影响训练与投机解码

MTP 不是「第 93–95 层」那种普通 decoder：它把上一层隐状态和下一个 token 的 embedding 拼起来，过一层 decoder，再用自己的输出头预测更远一个 token。三套结构完全相同，首尾串成一条链。

训练时

每一块都在多预测一步：主 LM Head 学 xt+1，MTP-1 学 xt+2，MTP-2 学 xt+3，MTP-3 学 xt+4。相当于给同一个隐状态加了三个「更远的监督」，逼模型在隐空间里提前规划。

推理时（投机解码）

主干一次前向得到 h → MTP 串行给出 3 个候选 token → 主模型并行验证，能接几个就接几个。官方最小实现直接不加载这 2.52 B，不开启就没有任何开销。

哪些是权重里读出来的、哪些是推断：层数（92/93/94）、每块包含 enorm / hnorm / eh_proj / 一个 decoder 层 / shared_head.norm + output、decoder 是滑窗注意力 + 稠密 MLP（13824，非 MoE）、每块 838.62 M——这些都能在 checkpoint 的 17 个张量里逐一对上。至于「拼接顺序、embedding 与主干共享、三层首尾串联」，是按 MTP 的通行接法推断的，官方推理实现没有加载这部分代码。
